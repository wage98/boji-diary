# 薄肌日记 · 竞品差距分析与优化路线（v7.6）

> 对照对象：**Keep**（课程+社区）、**Nike Training Club**（免费课程）、**Hevy / Strong**（硬核训练记录）、
> **MyFitnessPal / 薄荷健康**（饮食与热量）、**Fitbod**（自适应计划）、**wger / FitTrackee**（开源自建）。
> 维度：①功能完整度 ②交互体验 ③数据准确性 ④智能化程度。
> 结论口径：本产品定位是「**居家哑铃 + 桌宠陪伴**」的轻量 PWA，不追求大而全，差距分「必须补」「可后补」「不必补」三类。

## 二、差距清单（按优先级）

### P0（影响核心链路完成率，2 周内）
1. **饮食录入链路过长**：拍照后仍需搜索 → 增加「最近记录/常用食物」置顶一键复选，目标 2 步内完成。
2. **识别失败兜底文案与引导**：已实现（离线/空结果/超时均有提示），但需在 UI 明示「拍照=留档，热量需你确认」避免误解 —— 文案已加，需在引导页再强调一次。

### P1（功能完整度补课，1–2 个月）
3. **自定义动作**：允许用户新增动作（名称/组次/重量/视频链接），存入 `STATE.planEdits`。
4. **体重记录曲线**：按日期存体重数组，画趋势线，替代当前"手工改档案"。
5. **真·食物识别**：接 OpenFoodFacts 条码/名称 API（免费无密钥）或云端图像识别；离线回落本地库。
6. **历史食物/收藏**：记录用户常用食物，下次一键添加（同时解决 P0-1）。

### P2（体验与激励，按需）
7. 成就徽章体系（连续 7/30/100 天、首次 PR）。
8. 训练容量与 1RM 估算、PR 榜。
9. 定时训练提醒（需 Notification 权限，注意 iOS PWA 限制）。
10. 助手接 LLM API（需 key 与后端代理，涉及隐私与成本，谨慎）。

### 不必补（有意取舍）
- 账号/云同步：**与"数据仅存本机"的隐私承诺冲突**，保持本地优先。
- 社区/社交：定位个人工具。
- 内置视频：外链 B 站可自验，避免版权与体积问题。

## 三、结论

1. **最短板是"食物数据"而非"训练"**：训练侧（计划/记录/超负荷/打卡/月历/评分）已对齐 Hevy/Strong 的 70%；饮食侧只有 MFP/薄荷的 30–40%，且**真正的拍照识别依赖云端**——这是唯一无法靠前端单独解决的能力缺口。
2. **差异化的护城河是"桌宠陪伴 + 完全离线"**：主流 App 无一具备常驻桌宠情绪反馈，且都需登录/联网；这两点应当放大（成就系统、桌宠对连续打卡的更强反馈），而不是去追大而全。
3. **数据准确性要诚实标注**：本地估算误差 ±20–35%，UI 与助手回答中均已明示，避免用户把估算当精确值——这比假装精确更符合"不瞎编"的产品原则。
4. **下一版本建议聚焦 P0/P1 的 3、4、5、6 四项**（自定义动作、体重曲线、真识别、常用食物），预计可把功能完整度从当前的 ~60% 提到 ~75%，且都不破坏现有数据结构。

# 桌宠自绘二次元形象 · 方案对比与选型建议

> 背景：当前桌宠使用《原神》小练官方素材（公开仓库，溯源见 `assets/CREDITS.md`）。
> 若要替换为自绘形象，有三条可落地的技术路线。以下按「制作成本 / 技术门槛 / 可定制程度 / 与本项目契合度」对比。

## 前置约束（来自项目架构）

- 纯前端 PWA，**无构建、无依赖打包**；引入任何运行时库都会直接增大 `sw.js` 预缓存体积与首屏成本。
- 桌宠引擎现状：8 情绪状态机 + 打字机气泡 + 左右缘探头吸附 + 拖拽，**素材按「情绪 → 静态图」键值切换**（`assets/nahida-*.webp`）。
- 换形象的本质需求 = 一套可分情绪切换的小尺寸素材 + 适度动效（呼吸/眨眼级别的微动画即可，不做骨骼动画）。

## 三条路线对比

| | 方案 A：分层 SVG 组件 | 方案 B：Lottie 动画 | 方案 C：参数化形象生成器 |
|---|---|---|---|
| **思路** | 把角色拆成可复用图层（脸/眼/嘴/发型/身体/配件），情绪=图层组合 + CSS/SMIL 微动效；一个 SVG 文件内建全部情绪 | 用 After Effects 制作动画导出 JSON，前端引入 lottie-web 播放 | 写一个「捏脸」程序：发型/眼色/脸型/配色等参数 → 程序合成 SVG/PNG；可做成 App 内「我的桌宠」自定义功能 |
| **制作成本** | 中。基础形象 1–2 天；8 情绪靠图层复用，边际成本低 | 高。需 AE 技能或外包；每个情绪一条动画时间线，8 情绪工作量 ×8 | 前期高（生成器 1 周级），之后出形象近零成本 |
| **技术门槛** | 低：手写/设计工具导出 SVG 即可，现有桌宠引擎改一个 `setPetSkin()` 映射即可接入 | 中：前端简单（CDN 或本地 1 个库 ~250KB），瓶颈在 AE 制作端 | 高：生成器本身是个小软件，参数空间设计、合成、防呆都要做 |
| **体积** | 极小：单文件 20–60KB，图层复用不翻倍 | 大：每情绪 30–150KB JSON，8 情绪约 0.3–1MB，**SW 预缓存明显变重** | 小（产出 SVG），但生成器代码本身占体积（若放线上） |
| **可定制程度** | 高：换色/换发型/换表情都是改图层；后期可平滑演进成方案 C 的合成目标 | 低-中：改动画必须回 AE 重导出，无法在端上定制 | 极高：用户可自助捏形象，是产品级差异化功能 |
| **动效上限** | 中：眨眼/摇晃/弹跳足够；复杂飘动/头发物理较费 | 高：AE 里能做任意复杂动画 | 中：受合成规则限制 |
| **与本项目契合度** | ★★★★★ 零依赖、零构建、情绪映射天然对齐现有引擎 | ★★☆☆☆ 引入库 + 体积负担与「无依赖」原则冲突 | ★★★☆☆ 很诱人但当前阶段过重，可作远期目标 |

## 结论与推荐

**推荐方案 A（分层 SVG 组件）**，理由：

1. **体积与架构零冲突**：不引入任何库、不加重 SW 缓存，符合「纯前端无构建」的既定架构。
2. **接入成本最低**：现有桌宠引擎只改「情绪 → 素材」映射层（新增 `setPetSkin()`，官方素材与自绘皮肤可共存切换），不动状态机、不动拖拽/吸附逻辑，改动面小、可回滚。
3. **情绪复用天然匹配**：8 情绪在本方案里是「眼睛/嘴/眉毛图层 + 1–2 个 CSS 微动效」的组合，而不是 8 条独立动画，边际成本最低。
4. **保留升级路径**：分层 SVG 正是方案 C 的合成原料——未来若要做「捏桌宠」功能，直接在 A 的图层体系上加参数化合成即可，不返工。

不推荐 B（Lottie）：体积与依赖代价换来的动效上限，对一个 60px 桌宠来说是过剩能力；不推荐现在上 C（参数化生成器）：产品价值大但工程量是一个独立功能模块，应等核心链路（识别/记录）稳定后作为 P2 立项。

**落地顺序建议**：先出 1 个基础形象 + 3 情绪（开心/期待/睡觉）验证接入 → 通过自检回归 → 再补全情绪 → 最后视需求把图层开放成捏脸参数。

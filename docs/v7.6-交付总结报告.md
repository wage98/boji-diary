## 第三章 · 稳定性保障

### 3.1 自检机制

```
node tools/selfcheck.js
  ├─ tools/selfcheck-functional.js   41 项（功能回归：真点按钮/真按键/真读字节）
  └─ tools/selfcheck-attack.js       51 项（攻击式：边界值/异常输入/脏数据/失败兜底）
```

行为级测试（jsdom + `runScripts:'dangerously'` 注入 app.js），不是静态断言。纪律：新增功能必须同时补一条攻击式用例。

### 3.2 本轮发现并修复的 6 类真实缺陷

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| A11 | 体重填 1e9 → 目标热量百万、蛋白为负 | `dailyGoal()` 无上限 | 体重夹取 `[30,200]`，越界回落默认值 |
| A12 | `selDate='abc'` → 训练页崩溃 | `getDayType(NaN)` → `PLANS[undefined].ex` | `getDayType` 校验 0–6，非法回落 `'rest'`；`renderTraining` 加 `planSafe` 兜底 |
| B3 | 份数输入 `-5` / `1e9`，输入框显示与内部值不一致 | 只在 `input` 时算值，不回写 | 新增 `change` 事件规范化回写 |
| E3/E6/E7/E8 | **助手不接上下文、不结合本机数据、兜底失效** | **新旧 `nahidaReply` 同名重复定义**，函数提升后旧版覆盖新版，新逻辑整段变死代码（`node --check` 查不出） | 删除旧版函数，保留新版（KB 42 条 + `CTX` 上下文 + `FOLLOW_RE` 追问识别 + `dataReply` 结合数据） |
| — | 记录份数语义错乱（本地条目被预乘） | 保存时统一预乘 | 本地库保留「每份」基准 `q=份数`；在线条目按克预乘后 `q=1`，克数写入名称 |
| — | 食物库两条基准偏差 | 数据源不准 | 汉堡 `p18,c40,f22`→`p18,c42,f28`（430→492 kcal）；薯片→`薯片(1包/70g)` `p4,c38,f26`（316→402 kcal） |

### 3.3 攻击面覆盖清单

- **A 组 脏数据 / 边界值**：localStorage 任意字段为 null/undefined/NaN/负数/超长字符串/错误类型
- **B 组 异常输入**：份数、体重、身高、哑铃重量的极端与非数字输入；XSS 注入串（断言 `img[src="x"]` 与 `[onerror]` 节点数为 0）
- **D 组 网络失败兜底**：`fetch` reject / 返回非 JSON / 空结果 / 无 `fetch` 环境 → 必须给出兜底文案且不崩
- **E 组 助手鲁棒性**：空输入、1 万字符、未知问题（必须回「不太确定」而非瞎编）、上下文连续性
- **F 组 回归护栏**：层栈返回键、月历打卡、饮水 ml、休息计时器、时间戳出处说明

## 第四章 · 竞品差距分析（结论）

对标 Keep / Hevy / MyFitnessPal / 番茄 ToDo（交互参照）。

| 维度 | 我们的位置 | 主要差距 |
|---|---|---|
| 功能完整度 | 训练计划 + 打卡 + 月历 + 评分 + 桌宠已闭环 | 缺自定义动作、体重曲线、训练容量/1RM、成就系统 |
| 交互体验 | 卡片式、连续天数激励、返回键层栈，接近番茄 ToDo | 饮食录入 5 步偏长（P0）；缺常用食物一键复选 |
| 数据准确性 | 训练侧准确（用户自填组次重量） | **饮食侧是短板**：本地库 81 项 + 拍照仅留档，热量估误差 ±20–35%，必须诚实标注 |
| 智能化 | 知识库 42 条 + 多轮上下文 + 结合本机数据 | 无真图像识别、无 LLM、无自动计划调参（渐进超负荷仅单条建议） |

**结论**：护城河是「桌宠陪伴 + 完全离线 + 数据仅存本机」；最大短板是食物数据。优化路线按 P0（饮食录入提速、引导页写明拍照能力边界）→ P1（自定义动作、体重曲线、真识别、常用收藏）→ P2（成就、容量/PR、提醒、LLM）推进。完整表见 `docs/竞品差距分析.md`。

## 第五章 · 重点攻坚

### 5.1 拍照识别食物（自查三遍以上）

**诚实边界（必须先说清）**：当前是**「拍照留档 + 本地/在线库匹配 + 用户校正」**，**不是**离线端侧 AI 图像识别——纯前端无后端、无模型，做不到就是做不到，不做假按钮。

| 自查项 | 结果 |
|---|---|
| 识别准确率 | 拍照本身不做识别；识别靠搜索匹配本地库 + OpenFoodFacts 在线查询。第一遍自查发现「拍照后无任何校正入口」→ 已补；第二遍发现「校正面板无照片时不可用」→ 已补（D7）；第三遍发现「份数语义错乱」→ 已修 |
| 食物库覆盖度 | 34 → **81 项**（蛋白/主食/蔬果/家常菜外食/坚果油脂饮零食五类），并校准两条偏差数据 |
| 营养估算误差 | 本地库为「每份」基准，误差主要来自份量估计，标注 ±20–35%；已在 UI 明确出处 |
| 识别失败兜底 | **4 类全部有用例**：网络 reject / 非 JSON / 空结果 / 无 fetch 环境（D1–D3、D8）→ 统一兜底文案，不崩不空窗 |
| 手动修正流程 | 名称可改、份量 ±、**热量可手动覆盖**（`kcalFix` 优先于公式推算）、可在线查询补全、照片缩略随条目展示 |
| 在线查询 | OpenFoodFacts 公开 API（免费无密钥），AbortController **7 秒超时**；条目按克预乘后 `q=1`，克数写进名称避免歧义 |

### 5.2 智能助手

- 知识库 **18 → 42 条**：训练（动作/强度/疼痛）/ 营养（蛋白/热量/饮水）/ 计划制定（分化/渐进超负荷）/ 恢复（睡眠/拉伸）/ 常见问答；其中 **16 条带 `more` 追问补充**
- **多轮对话**：新增 `CTX` 上下文与 `FOLLOW_RE` 追问识别，连续提问能接着上一轮答
- **结合本机数据**：`dataReply(q)` 会读 `STATE`（连续天数、今日完成、饮水、目标）作答，例如「我练得怎么样」→ 报连续打卡
- **兜底**：未知问题回「不太确定」并给可执行建议，**不瞎编**（E8 有对应用例）
- 修复最大隐患：删除重复定义的旧 `nahidaReply`

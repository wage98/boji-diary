# 训练日记 · 经验总结

> 一款以“手机桌面常驻二次元桌宠”为核心的健身 App 原型（v2 → v7.2.1）
> 角色：小练（《原神》官方素材，溯源见 `assets/CREDITS.md`）
> 技术：纯前端单页 + localStorage，无构建步骤；CSS 变量 token 体系贯穿全程

## 一、我们最终交付了什么

- **桌宠即主界面**：小练常驻手机桌面，承担陪伴 + 引导 + 记录三合一。
- **BongoCat 式左右缘探头吸附**：角色直立、头朝屏内（非吸附侧），半身被屏幕边缘裁切探出；拖拽松手自动吸附较近一边，沿边位置跟随拖拽点；悬停向屏内多探头一点。
- **情绪与陪伴引擎**：8 种情绪态（开心/期待/加油/骄傲/委屈/思考/睡觉/招手）+ 打字机气泡（逐字显示、读完整再消失、随机不重复台词）。
- **五个功能模块**：训练（周历 + 每日动作 + 标准/注意 + B站章节深链 + 完成打卡）、饮食（食物库 + 饮水）、数据（连续/动作趋势）、我的（档案 + 重置）、聊天（内置 18 条带证据等级的问答）。
- **首页“桌宠之家”**：时钟 + 今日三连 + 今日训练速览卡（动作 chips + 进度条，一点进训练），一眼看到每天练什么。
- **视觉**：二次元玻璃拟态、低饱和柔和渐变、去塑料感（v7.1 起）。

## 二、关键决策与踩过的坑

1. **角色素材：自用 ≠ 可随意原创**。即使你说过“自用不涉及版权”，我们仍选择可溯源的官方角色（小练）而非原创形象，规避任何风险，并在 `CREDITS.md` 标注出处。
2. **桌宠朝向：90° 旋转 = 翻车**。最初按你给的 BongoCat 截图做了四边旋转探头（顶缘倒挂 180°、侧缘 ±90°），你一眼反馈“怪”。教训：**人物立绘贴边只需“直立 + 水平镜像让脸朝屏内”，绝不做 90°/180° 整身旋转**。最终收敛为仅左右两缘吸附。
3. **“看不到每天动作”是反复出现的硬需求**。v5、v7 都反复被提。根因早期是“周日=休息日什么都不显示”+ 日期锁死。修复：周历 7 天全可点、完整列出动作/标准/注意事项，并在首页加速览卡。
4. **CSS 变量名要稳定，只改值**。多轮迭代中保持 `--mint/--pink/--ink...` 等变量名不变、只调数值，避免改样式断裂 JS 里 `style.transform` 等内联引用。
5. **深链要可自验**。训练动作全部映射到卓叔 B站合集的真实章节时间戳（`?t=秒`），点开即可核对，不靠“凭感觉”。
6. **外部爬取受限**：抖音链接需 App、Fandom 有 Cloudflare。最终通过 Fandom API + Referer/UA 拿到官方 webp 直链；不可达内容如实告知，不编造。

## 五、给后续接手者的提醒

- **真实 Live2D 替换**：需拿到小练授权 Cubism 模型（`.moc3`+`.model3.json`+纹理），把 `#pet` 内 `<img>` 换为 `<canvas>` 并接 Cubism Web SDK；当前 CSS 动画方案可直接平移为“待机/情绪”驱动层。
- **PWA 图标兼容性**：现用 SVG 图标，现代浏览器足够；若要覆盖老旧环境，补 192/512 PNG（需引入图像库生成）。
- **计划存储粒度**：现按 dayType 覆盖；若要“逐日独立计划”，把 `planEdits` 键从 dayType 改为日期即可。

## 六、v7.4 移动端专项：三个值得复用的教训

1. **`'use strict'` 下，模板字符串里的一个变量名笔误 = 整块功能静默失效**
   本次「饮食」点击无响应，根因是 `${mf}`（应为 `fTot`）。严格模式下读取未声明变量抛 `ReferenceError`，而它没有 try/catch 包裹，导致整条调用链中断 —— **表现在用户侧不是报错，而是「点了没反应」**。
   教训：这类"哑掉"的故障最难自查。**凡是批量渲染的模板字符串，务必跑一次真实的 render（哪怕用 jsdom）**，光靠肉眼/静态检查抓不到。

2. **移动 Web 的"返回键"不是浏览器免费给的，必须自己建层栈**
   返回键的行为 = `history` 状态管理。可靠的最小骨架是三个变量：层栈 `stack`、自己压入的条目数 `g`、以及 UI 关闭时用于抵消 popstate 的 `suppress` 计数。两个易错点：
   - **哨兵条目必须压在本层之前**（顺序反了会先弹哨兵，表现就是"按返回直接退出了"）；
   - **UI 上的 ✕ 也必须走 history 回退**，否则"按返回关 N 层"和"点 ✕ 关 1 层"会各记各的账，堆栈错位。

3. **SW 的"缓存优先"会让新版延迟一次启动才生效**
   做 PWA 时常为了秒开把 app shell 全设成 cache-first，代价是用户发版当天看不到更新。**页面类请求（navigate / accept: text/html）必须网络优先**，静态资源才用缓存优先 —— 这样既保留离线能力，又能保证"下次打开就是最新版"。这一次直接决定了用户是否需要手动刷新。

4. **验证纪律的下限是"跑起来"**
   本轮 52 项验证里，真正抓出问题的是 **jsdom 行为级模拟**（真点按钮、真按返回键、真导出 CSV 看字节）。仅靠 `node --check` + 字符串断言只会证明"代码里写了这句话"，证明不了"功能真的好使"。另外两条误判也值得记：带引号的检查串容易被 shell 转义坑导致「假 FAIL」，以及 `Blob.text()` 会吞掉 BOM（要用 `arrayBuffer()` 按字节校验）。


## 七、v7.5 需求评审：三条边界与两个参考系

1. **“拍照识别食物热量”在纯前端离线 App 里做不到真 AI 识别**
   本轮需求要求“拍照自动识别食物并估算热量”。没有云端 API（或本地模型）时，任何纯 JS 方案都只能做到“估算”而不是“识别”。交付口径定为：**拍照留档 + 34 种常见食物估算库快速选取 + 名称/份量/热量全字段手动校正**，并把真识别 API（OpenFoodFacts Search API 免费无钥匙可查条码/名称、或接云端图像识别）写进后续方向。**如实告知能力边界，好过做一个假装会识别的假按钮。**

2. **“实时修改档案”的联动面要先算清再动手**
   身高/体重/哑铃重量在数据模型里是下游多处计算的输入（建议起始重量 suggKg、每日蛋白/热量/饮水目标、渐进超负荷基准）。这次通过把写死的 `DAILY_GOAL` 改成 `dailyGoal()` 函数一次性收口，档案一处改动全链路自动生效——**散落的硬编码常量是“改 A 处忘 B 处”类 bug 的根源，先收口再开放编辑。**

3. **编辑态不要整页重渲染**
   档案编辑用 `oninput` 直接写 STATE + 更新头部显示，而不是重渲染整个面板——否则手机上每敲一个字输入框就失焦。评分器同理：点星只切 class，不重建 DOM。

4. **参考开源项目（本轮知识库更新依据）**
   - **wger**（github.com/wger-project，GPL）：开源健身/体重记录，其“计划-动作-重量记录”数据结构验证了本项目 `planEdits/exLast` 的做法可行。
   - **OpenFoodFacts**（openfoodfacts.org）：开源食物数据库，REST API 免费，是后续做真·食物热量查询/拍照识别的首选数据源；知识库“食物热量怎么估算”词条即引用其公开数据。
   - **番茄 ToDo**：本轮统计页的交互参考系——统计格 + 连续天数激励 + 月历打卡视图，均为其验证过的成习惯养成设计。
